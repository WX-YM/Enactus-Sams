# 03 — Locales, UTF-8 and text

## 1. The locale seam

An application declares its locales; anvil gives them a type. The full mechanism
is in [`01-seams.md`](01-seams.md) §2 — including why this one forces anvil to be
a source dependency. The rules that follow from it:

**The order is persisted.** A locale's index is byte 3 of every access token and
the value stored in the user row. The table is append-only: never reorder, never
remove. This is the same rule permission bits live under, and it fails the same
way — silently, by reinterpreting rows that are already written.

**An unknown tag resolves to nothing, not to the default.** Answering an
unrecognised `?lang=` in the default locale is how a missing translation goes
unnoticed for a year.

**`complete()` treats present-but-empty as missing.** A blank string renders as a
blank heading in that locale and nothing reports it. A missing translation is a
validation error, never a silent fallback — a fallback shows a reader the wrong
language without telling them.

**`get()` is an array index.** Not a branch, not a hash. `Locale`'s only
constructors validate, so an out-of-range locale is unrepresentable and there is
no bounds check to forget on the render path.

## 2. UTF-8 is validated once, at the edge

`i18n/utf8.h` wraps simdutf. Validation happens **before** the JSON parse, so
every `string_view` that comes out of the parser is known-valid UTF-8 and nothing
downstream re-checks.

Strict means strict. Four shapes a lenient decoder accepts are rejected:

| Shape | Why it matters |
|---|---|
| Overlong encoding (`C0 80` for NUL) | Two encodings of one character means two filters can disagree about what the input says |
| Lone surrogate (`ED A0 80`) | Not a valid scalar value; some decoders pass it through |
| Truncated sequence | A trailing partial character at a buffer boundary |
| Beyond U+10FFFF (`F5 …`) | Outside Unicode entirely |

Each is a parser-differential primitive: if this layer accepts what a later one
rejects, or the reverse, the two disagree about the content — and a security
decision made on one reading is enforced on the other.

`truncate_to_code_point` cuts a string at a character boundary, never mid-sequence.
A truncation that splits a multi-byte character produces invalid UTF-8 from valid
input, which is a way to fail validation downstream that has nothing to do with
what the user typed.

## 3. Code points, never bytes

Every text bound in this library counts code points.

A byte limit is not a smaller limit for non-Latin text — it is a **different**
limit, and the difference is roughly a factor of two for Arabic, three for most
CJK. A 200-byte "short prose" field accepts about 200 English characters and about
66 Chinese ones, and nothing in the error message says so.

Counting code points costs one pass that simdutf already does. It is not a
performance question.

## 4. Digit folding

`fold_digits` maps Arabic-Indic (U+0660–U+0669) and Extended Arabic-Indic
(U+06F0–U+06F9, used for Persian and Urdu) onto ASCII digits, into a **stack
buffer**.

It runs before every numeric, date and identity check. A user typing a phone
number or an identifier on an Arabic keyboard produces those code points, and a
validator that rejects them is a validator that rejects that user for typing their
own language.

This is i18n machinery, not locale-specific: the folding is correct wherever those
digits appear, and it is applied unconditionally rather than gated on the request's
locale — the keyboard and the `Accept-Language` header are not the same fact.

## 5. Bidirectional control characters

`i18n/bidi.h` strips and classifies the Unicode bidi control characters
(U+202A–U+202E, U+2066–U+2069).

These are invisible and they **reorder rendered text**. A display name containing
a right-to-left override renders as something other than what is stored, which
means a moderator approving a name and a reader seeing it are not looking at the
same thing. In a filename it is the classic extension-spoofing trick.

`TextClass` reports whether a string is left-to-right, right-to-left or mixed,
which is what a field bound rule uses to decide whether a mixed-direction value is
plausible for that field.

## 6. Normalisation and confusables

`i18n/normalize.h` wraps ICU.

**NFC** for anything stored or compared. "é" has two encodings — one code point, or
"e" plus a combining acute — and they are different byte strings that render
identically. Two spellings of one value must produce one digest, or a blind index
silently stops matching and duplicate detection quietly stops working.

**NFKC plus folding** for identity comparison, where the question is "are these the
same person's input" rather than "are these the same string".

**Confusable detection** via ICU's `uspoof`. A Cyrillic "а" and a Latin "a" are
different code points that render identically, which is the homoglyph attack —
`pаypal.com`. Note that `check_email` already rejects non-ASCII domains outright,
so for email this is defence in depth rather than the primary control.

## 7. Sorting and collation

A locale that needs linguistic ordering carries an ICU collation string;
`LocaleSpec::collation` is empty for locales where binary comparison is correct,
which is faster and is the right answer for most Latin text.

**The query and the index must carry the same collation.** MongoDB will not use an
index built with a different one, and the symptom is a `COLLSCAN` — slowness, not
an error, discovered under load rather than in review. `db/collation.h` hands both
sides the same `LocaleSpec::collation` so they cannot disagree.

## 8. JSON output

`http/json_writer.h` emits **raw UTF-8, never `\uXXXX`**.

Most JSON writers escape non-ASCII by default. That turns every Arabic character
from 2 bytes into 6 — a threefold inflation on the hottest public endpoint in a
bilingual application, for no benefit: the response already declares UTF-8 and
every JSON parser written this century reads it.
